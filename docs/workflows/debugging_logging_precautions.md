# Debugging logging precautions
1.  **Inconsistent Logging API Usage & Level Precedence:**
    *   **Concern:** The codebase exhibits a mix of logging approaches:
        *   Direct calls to the Pino instance's methods (e.g., `logger.info()`, `logger.error()`) are prevalent.
        *   The `log(DEBUG_LEVELS.LEVEL, ...)` compatibility function (a named export from `logger.js`) is also available and used in some places (e.g., `endGame.js`).
        *   The `logger.js` module itself determines the initial log level based on `process.env.LOG_LEVEL` (Pino's native level) or `process.env.DEBUG_LEVEL` (your custom numeric level).
    *   **Debugging Impact:** This inconsistency can lead to confusion regarding which environment variable truly controls the verbosity of all logs. If `LOG_LEVEL` is set (e.g., to `warn`), direct `logger.info()` calls will be suppressed. However, if `DEBUG_LEVEL` is set (e.g., to `INFO`), the `log()` function might still attempt to call `logger.info()`, which could then be suppressed by the `LOG_LEVEL` setting. Developers might struggle to get the desired log output if they don't understand this precedence and the dual API.
    *   **Why it's new:** `debugging_precautions.md` advises using "the project's logger utility" but doesn't differentiate between its various exports or the implications of mixing them with environment variable precedence.

2.  **Semantic Mismatch in `log` Function's Numeric Levels:**
    *   **Concern:** The `log` function in `logger.js` maps your custom numeric `DEBUG_LEVELS` to Pino's string levels (e.g., `DEBUG_LEVELS.ERROR` maps to `logger.error`). However, the numeric values themselves (e.g., `1` for `ERROR`) are sometimes used with messages that are semantically informational. For instance, `endGame.js` calls `log(1, "[checkGameOver] Checking for game over condition")`. A message like "Checking for game over" is typically `info` or `debug`, but `1` forces it to be logged as an `error`.
    *   **Debugging Impact:** This leads to "false positive" errors in logs, making it harder to identify genuine critical issues. Log analysis tools (like Splunk or ELK stack) will flag these informational messages as errors, cluttering dashboards and potentially triggering unnecessary alerts. Developers might ignore actual errors if the "error" stream is constantly filled with non-critical messages.
    *   **Why it's new:** This is a semantic issue with the *content* of the log message not matching the *severity level* it's assigned, which is a deeper problem than simply using `console.log`.

3.  **Dynamic Log Level Changes Are Not Supported (Pino Limitation):**
    *   **Concern:** The `setDebugLevel` function is exported by `logger.js` and attempts to change the log level dynamically. However, its implementation explicitly logs a warning stating: "Pino logger level ('${logger.level}') is set at initialization. Restart with new LOG_LEVEL or DEBUG_LEVEL env var to change."
    *   **Debugging Impact:** Developers might attempt to change log verbosity at runtime (e.g., via an admin command, a debug API endpoint, or even directly calling `setDebugLevel` in code) expecting immediate effect. When the logging behavior doesn't change, it leads to frustration and wasted debugging time trying to understand why their dynamic configuration isn't working, despite the warning in the logs.
    *   **Why it's new:** `debugging_precautions.md` focuses on architectural purity and avoiding `console.log`, but doesn't delve into the limitations of the chosen logging library (Pino) regarding dynamic configuration.

4.  **Inconsistent Structured Logging Practices:**
    *   **Concern:** While `logger.js` (and Pino itself) supports structured logging by accepting an object as the first argument (e.g., `logger.info({ gameId: 'abc', player: 'xyz' }, 'Player joined')`), many direct `logger.info()` or `logger.error()` calls throughout the codebase only pass a string message, or a message followed by an error object (e.g., `logger.error('Error occurred', err)`). The `log` function does attempt to use the object argument if provided (`if (obj) logger.error(obj, message); else logger.error(message);`).
    *   **Debugging Impact:** This inconsistency makes log aggregation, searching, and analysis significantly harder. When using log management tools, it's difficult to reliably query for specific contextual data (like `gameId`, `playerRole`, `errorCode`) if it's not consistently placed within a structured JSON object. Some logs might have a `msg` field, others a `message`, and others might embed context directly in the string.
    *   **Why it's new:** `debugging_precautions.md` doesn't address the *format* of the log message content beyond avoiding `console.log`. Structured logging is a best practice for modern applications, especially in a multiplayer server context.
